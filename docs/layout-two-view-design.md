# 双视图布局：镜头视图 + 俯视摆位（设计稿）

> 状态：**设计稿，未实现**（2026-11-11，同日第二版：翻页切换 + 米制测量 + 站立高度）。
> 3D 路线仍然搁置（[`layout-3d-design.md`](layout-3d-design.md)）；本文是它的轻量替代：
> 不做三视图、不做房间体块，只把"深度、朝向、真实尺寸"补进 2D 布局。
> 现有链路（工作台出模板、画布改框、提交回工作台、核对模板）见
> [`layout-workspace-design.md`](layout-workspace-design.md)。

## 0. 结论

两个 2D 视图就够，但**它们必须是同一个场景的两张投影**，不是两张各自独立的框：

- **镜头视图**：成图的那一张。管左右位置、画面占比、谁的哪一部分被裁掉。
- **俯视摆位**：不进成图。管前后深度、朝向、谁在地面 / 台阶 / 台口之下。

平视机位（pitch ≈ 0）下，三个轴正好分完：

| 方向 | 镜头视图 | 俯视图 |
| --- | --- | --- |
| 左右 X | 水平位置 | 水平位置 |
| 上下 Y | **离地高度** | — |
| 前后 Z | — | **深度** |

镜头视图的竖直方向本身就是立面：框的底边是接地位置，顶边是物体高度。
三视图里那张侧立面在这里是多余的。**代价是它只在平视时成立**；仰拍 / 俯拍会让
竖直方向同时混进高度与深度，那时才需要第三张图（本设计不做）。

两个视图**不并排、不弹窗**，像画廊详情的翻页一样来回切换（见 §3.0）：
并排会把两张图都压小，而俯视图需要的是米格，不是缩略图。

## 1. 目标与非目标

**目标**

1. 模型拿到的不是"几个 2D 框"，而是一段确定的**场景块**：层序、遮挡、支撑、朝向、光位。
2. 用户能在俯视图里把"合唱团在身后、站在台阶上"这种关系摆出来，而不是写进 caption 里赌模型读懂。
3. **尺寸用米，不用归一化深度**：用户给"站立高度 1.68 米"就能定这个人在画面里该多高；
   `0~1000` 只作为镜头框的内部单位，世界长度一律是米。
4. 现有出口不破：MOSS 布局 JSON 仍只吃镜头视图的轴对齐框；核对模板仍只对照镜头视图。

**非目标**

- 不做三视图、不做侧立面、不做房间墙角、不做体块 / 深度图（已证伪，见 `layout-translator.md`）。
- 不做任意斜面 / 非盒体。琴盖这种绕水平轴打开的平面，本设计只能记一个 `tilt` 提示，
  真正的几何留到以后。
- 不要求模型做投影。投影与求解都在前端 / 后端做，模型只读结果。
- 不改 MOSS 的 `bbox` 契约。

## 2. 场景模型

### 2.1 坐标与单位

- 世界坐标：**X 向右，Y 向上，Z 远离相机**（右手系，相机看向 +Z），单位**米**。
- 相机在 `(0, eye, 0)`，平视，无 roll；主点在画面 `(0.5, horizon)`。
- 镜头视图里的框仍用 `0~1000` 归一化（与 `layout_spec.dart` 一致），
  但这只是**投影结果的存储格式**：宽度按画面宽归一化、高度按画面高归一化。
- 俯视图直接用米：横轴 X、纵轴 Z，画 0.5 / 1 / 2 米的网格，不再出现 `0~1000`。
- 世界长度只在镜头视图边界、场景块与校验里换算成像素；MOSS JSON 仍只接 2D 框。

### 2.2 相机

```jsonc
"shot": {
  "width": 1024,
  "height": 1024,
  "eye": 1.55,          // 视高（米）
  "fov": 50,            // 水平视场角（度）；默认 50°，UI 上叫「35mm 广角档」
  "horizon": 0.48,      // 地平线在画面高度的比例；0.5 = 正中
  "yaw": 0              // 机位朝向（度）；MVP 固定 0
}
```

`horizon` 用**主点偏移**实现，不是俯仰：它等价于移轴镜头，竖线仍然竖直。
真正的 pitch 留到以后；本设计假定相机水平。

### 2.3 框

```jsonc
{
  "id": "r1",
  "label": "钢琴演奏者",
  "kind": "character",

  "x": 40, "y": 120, "w": 300, "h": 700,   // 镜头视图（0~1000，投影结果）

  "z": 2.4,             // 米：框中心到相机的深度
  "base": 0,            // 米：底边离地高度（台阶 / 台口用正负号）

  "standingHeight": 1.68,   // 米：人物站立高度（每份布局手填，不读角色卡）
  "pose": "standing",       // standing / sitting / kneeling / lying
  "height": 1.68,           // 米：画面里的实际高度（默认 = 站立高度 × 姿态系数）
  "width": 0.5,             // 米：肩宽 / 物体宽（默认按 kind）
  "depth": 0.3,             // 米：脚印进深（默认按 kind）
  "yaw": 15,                // 度：朝向，0 = 面向相机

  "lock": "height",         // height / depth：哪一个是你亲手定的真源
  "estimated": false        // true = 数值来自画面推算，不是用户填的
}
```

镜头框 `x/y/w/h` **默认是投影结果**，不是独立真源。由相机、`z`、`base`、
`height/width/depth` 与 `yaw` 投影得到；用户拖动时再反解回上面几个量（§2.4）。

身高、姿态、镜头都跟着布局规格一起存：存进本地布局库之后，复用同一份布局不用重填；
只有新建一份布局才要重新填。

### 2.4 投影与求解

```
f   = (shot.width / 2) / tan(fov / 2)      // 像素焦距
cx  = shot.width / 2
cy  = shot.horizon * shot.height

sx  = cx + f * X / Z
sy  = cy - f * (Y - eye) / Z
```

一个框的投影高度（像素）：

```
h_px = f * H / Z
```

于是三个量里知道任意两个就能求第三个：

```
Z = f * H / h_px          // 知道画面高度 + 真实高度 → 求距离
H = h_px * Z / f          // 知道距离 + 画面高度 → 求真实高度
```

底边高度与左右位置：

```
X = (sx - cx) * Z / f
base = eye - (sy_bottom - cy) * Z / f
```

`h_px = f · H / Z` 按**轴向距离**算；物体偏离画面中心较大时是近似值
（误差约 `(X/Z)² / 2`），布局够用。真要精确就按角点投影，P0 不做。

「站立高度」与「画面高度」是两件事：`standingHeight` 是身份事实（这个人多高），
`height` 是画面里实际占的高度（坐着、跪着、被裁掉一截都会更小）。
`pose` 给一个粗系数，把站立高度折算成画面高度：

| 姿态 | 系数 | 说明 |
| --- | --- | --- |
| `standing` | 1.00 | 站直 |
| `sitting` | 0.55 | 坐姿（椅面到头顶，约） |
| `kneeling` | 0.65 | 单膝或双膝跪 |
| `lying` | 0.25 | 躺卧时画面里的竖直高度 |

系数只是初值，用户可以在检查器里直接改 `height`；改过之后 `estimated=false`、
`pose` 不再覆盖它。**提示词与场景块用 `standingHeight` 说"这个人多高"，
用 `height` 算投影**——不要拿站立高度当画面高度去投。

### 2.5 画幅裁切

投影出来的框可能有一部分在画面外（平视近景最常见：脚在画框下方）。规则：

- 米制字段（`z` / `height` / `base`）保存**完整**的物理事实，不因裁切改变；
- 镜头视图的 `x/y/w/h` 保存**可见部分**（夹进 0~1000），另用
  `clipped: ["bottom"]` 记录哪几条边被裁；
- 场景块要说明"下半身在画面外"；核对时只对照可见部分；
- **被裁掉的那条边不能用来反解尺寸**（拖动会失真），改数值请用检查器；
- MOSS 导出的就是可见框（它只认画面内的框）。

### 2.6 光

```jsonc
"light": {
  "key": "frontLeft",   // frontLeft / frontRight / backLeft / backRight / top
  "height": 2.4,        // 主光高度（米）
  "color": "amber"
}
```

光不进投影，只进场景块与提示词自检："主光在左前方"与"合唱团正面被照亮"必须一致。
光位仍是粗档，不做灯具几何。

## 3. 两个视图

### 3.0 切换：像画廊详情一样翻页

两个视图共用**一页画布**，用 `lib/widgets/paged_swipe.dart` 的 `SwipePageView` +
`PageBar` 切换，和画廊详情翻页同一套：

- 桌面（鼠标优先）：关掉滑动，用 `PageBar` 的「上一页 / 下一页」按钮；
- 手机：左右滑动切换，360 宽时 `PageBar` 只显示图标；
- 两页在过渡时同时存在，动画结束才注销旧页（`SwipePageView` 的既有契约）；
- **页面不持有数据**：两页都读写同一个 `LayoutScene`；选中框与每页的缩放 / 滚动
  存在父级，所以翻页、甚至旧页被注销之后也不会丢；
- 页序固定：**镜头视图在前，俯视摆位在后**，`PageBar` 文案就是这两个词。

不并排的理由：俯视图要看清米格与朝向，并排后每边只剩一半宽；翻页则每张都是全宽。

### 3.1 镜头视图

- 显示：框、名称、关系、地平线、可选的透视网格。
- 编辑：拖 = 左右 X；上下 = 底边高度（`base`）；缩放 = 按 `lock` 改 Z 或 H（§3.3）。
- 出图核对只认这一张。

### 3.2 俯视图

- 正交投影：横轴 X，纵轴 Z（近在下、远在上），网格以米为单位。
- 每个框画成**带朝向的脚印**：宽 = `width`，深 = `depth`，按 `yaw` 旋转；
  中心在 `(X, Z)`。
- 编辑：拖 = X / Z；旋转手柄 = `yaw`。
- 显示：米格、相机位置与视锥、台阶 / 台口的基准线、每个脚印上的高度标注（米）。
- **不出图、不进核对模板**。

### 3.3 联动与锁

两个视图共享同一个 `id`，改一个，另一个重画。**哪一个是真源由 `lock` 决定**：

| `lock` | 真源 | 镜头视图里改高度 | 俯视图里改深度 | 检查器 |
| --- | --- | --- | --- | --- |
| `height`（人物默认） | 站立/画面高度 | 解出新的 `z` | 改 `z`，画面高度跟着变 | 高度可改，距离是派生值 |
| `depth`（道具默认） | 距离 | 解出新的 `height` | 改 `z` | 距离可改，高度是派生值 |

其余动作不受锁影响：镜头视图左右拖 = X，上下拖 = `base`；俯视图左右拖 = X，
旋转 = `yaw`。

**默认锁**：`character` 用 `height`（人物身高是稳定事实），其它用 `depth`
（道具摆在哪儿更稳定）。用户可以在检查器里一键换锁。

**旧数据 / 只画了一个框**时：用 `kind` 的默认身高（人物 1.68 米、桌子 0.75 米、
其它 1.0 米）把 `z` 解出来，并标 `estimated=true`，检查器显示"按画面推算"。

## 4. 场景块（给模型的事实）

模型不读两张 2D 图，读后端算好的这一段：

```text
镜头：平视，视高 1.55 米，水平视场 50°，地平线在画面 48%。
光：主光在左前方，暖琥珀；环境是冷蓝灰。
层序（由近到远）：
1. 钢琴演奏者：前景，2.2 米远，站立身高 1.68 米、坐姿，画面中约 1.2 米，下半身在画面外，落地。
2. 三角钢琴：前景右侧，2.8 米远，高约 1.0 米，落地，琴盖朝右后方打开。
3. 合唱团：中景，4.5 米远，六人一排，站在 0.4 米高的台阶上，面向相机。
4. 观众：背景，9 米远，坐在台口以下 0.8 米处，背对镜头，只见轮廓。
遮挡：演奏者挡住合唱团左端；琴盖挡住合唱团右侧的一部分。
```

这段由**投影与排序**生成，不靠模型猜：

- 层序：按 `z` 排序，分成前景 / 中景 / 背景三档；
- 遮挡：镜头框相交 + `z` 更近的一方挡；
- 支撑：`base` 说"落地 / 站在 0.4 米高的台阶上 / 低于台口 0.8 米"；
- 朝向：`yaw` 映射成"面向相机 / 侧身 / 背对"；
- 尺寸：用米说"1.68 米高、2.2 米远、约占画面 82%"，不用像素。

模型拿到的工具正文 = 场景块 + 镜头视图框表。俯视图的原始 JSON **不发给模型**，
避免它把两张图当成两个构图去同时满足。

## 5. 与现有链路的关系

| 环节 | 现在 | 双视图之后 |
| --- | --- | --- |
| `layout_propose` | 只收镜头框 | 收镜头框 + 可选 `z` / `base` / `height` / `standingHeight` / `pose` / `yaw`；缺尺寸时按默认身高估一版并在 `issues` 里说明 |
| 核对模板 | 1 个模板，只有镜头框 | 仍只有镜头框；俯视图**不进** `layoutTemplates` |
| 提交闸门 | 按提示词原文比对 | 不变 |
| `LayoutResubmit` | 散文 + spec JSON | 散文 + 场景块 + spec JSON（米制字段一起带） |
| MOSS JSON | 镜头框直接转像素 | 不变；`yaw ≠ 0` 时按投影后的外接矩形导出，并记一条"旋转框有损" |
| 画布译者 | 一个框一段 | 按场景块的层序组织段落；仍然是"一个框一段"，校验器不用改 |

**为什么俯视图不进核对模板**：核对是拿产物和"成图应该是什么样"比。俯视图不是成图，
放进去模型会试图同时满足两张构图。俯视图只用于**写提示词之前**把空间摆对。

## 6. 校验（确定性，不靠模型）

1. **投影一致性**：`h_px = f · height / z` 与镜头框高度必须一致；不一致说明
   `z`、`height` 或镜头框有一处是手改坏的。P0 只报警，不自动改。
2. **遮挡与深度**：`relation=front` 的框，`z` 必须比被挡的框小。
3. **台阶 / 台口**：`base > 0` 的框必须能指出它站在什么上（台阶 / 舞台）；
   `base < 0` 的框必须落在台口以下；`base = 0` 时底边要落在该 `z` 的地面线上。
4. **站立高度与画面高度**：`height` 明显大于 `standingHeight`，或 `pose=standing`
   但 `height` 只有站立高度的六成，说明姿态与高度对不上，提示一句。
5. **光位**：`light.key=back*` 时提示词里出现"正面被照亮"就冲突（提示，不硬拦）。
6. **yaw 与 footprint**：俯视图里两个脚印大面积重叠、又没有前后关系时报警
   （与现有"重叠却没标谁挡谁"同一条纪律）。

校验结果进 `issues`，跟现有的夹边 / 清关系共用同一个出口。

## 7. 迁移与兼容

- `v: 2` 在出现米制字段时写入；`v: 1` 仍然能读。
- 缺 `z` / `height` 的框：按 `kind` 默认身高 + 镜头框高度解出 `z`，
  `base` 由镜头框底边解出，`estimated=true`，并记 `issues`
  （"距离是按 1.68 米身高从画面推算的，请到俯视图确认"）。
- 缺 `pose` → `standing`；缺 `yaw` → 0；缺 `width/depth` → 按 `kind` 默认。
- 旧的 `surface`（left/right/back/floor/table）只作为墙面的提示保留；
  地面 / 台阶关系改由 `base` 表达，两者冲突时以 `base` 为准并报警。
- 布局库、回传消息、`tool_result` 都要能读旧形状（`LayoutSpec.fromJson` 已经刻意宽容，
  新增字段继续走"认不出回默认"）。
- **不要**把米制字段写进 MOSS JSON；不要改 `bbox_coord_space`。

## 8. 界面

- 画布顶部：`PageBar`「镜头 / 俯视」+ 左右翻页按钮（桌面）；手机滑动切换。
- 镜头视图：框、地平线、透视网格；选中框可拖、可缩放。
- 俯视图：米格（0.5 / 1 / 2 米自动选档）、相机与视锥、台阶线、脚印与朝向箭头。
- 检查器（两页共用，选中框时出现）：
  - 站立身高（米，人物；**每份布局手填**，默认 1.68，不读角色卡）
    → 姿态（站/坐/跪/卧）→ 画面高度（自动，可手改）；
  - 距离（米）、底边（米）、宽 / 深（米）、朝向（度）；
  - 锁：高度 / 距离（一键切换，决定拖动时改哪一个）；
  - 派生值用灰字显示"按 1.68 米 / 2.2 米推算"，手改过的显示"手动"。
- 窄屏（< 900）：只显示当前页；检查器做成底部弹层，不常驻。
- 文案遵守 `AGENTS.md` §6.2：说"高度 / 距离 / 台阶 / 台口"，不说 `Z`、`FOV`、
  `principal point`。

## 9. 分期

| 阶段 | 内容 | 估时 |
| --- | --- | --- |
| **P0** | 米制数据模型 + 投影/求解 + 两页翻页壳（镜头仍可画框，按默认身高解 `z`；俯视只读）+ 场景块 + 校验 1/2/3 + 旧文件迁移 | 3~5 天 |
| **P1** | 俯视可编辑（拖 / 转）+ 检查器（站立身高 / 姿态 / 锁）+ 相机面板 + 镜头视图拖动反解 | 1~2 周 |
| **P2** | 投影细化（`yaw` 后的外接框）+ 光位校验 + `tilt` / 台口基准线 | 1 周 |
| **P3**（可选） | 斜面 / 平面图元（琴盖）、镜面平面、MOSS 旋转框的精确导出 | 按需 |

P0 结束就能回答"米制深度和站立高度是否解决了三栏拼贴"；P1 才让用户真的"翻着画两张图"。

| 对象 | `z` | `base` | `standingHeight` | `pose` | `height` |
| --- | --- | --- | --- | --- | --- |
| 钢琴演奏者 | 2.2 m | 0 | 1.68 m | sitting | 1.20 m |
| 三角钢琴 | 2.8 m | 0 | — | — | 1.00 m |
| 合唱团（六人一排） | 4.5 m | 0.40 m | 1.70 m | standing | 1.70 m |
| 观众（轮廓） | 9.0 m | -0.80 m | 1.70 m | sitting | 1.10 m |
| 灯 | — | 3.20 m | — | — | — |

表里的 `height` 是**完整**的画面高度；演奏者在 2.2 米、平视机位下脚会落到画框下方，
所以镜头框只存可见的上半身，`clipped=["bottom"]`，场景块写"下半身在画面外"。
俯视图仍按完整脚印画，不因裁切缩短。演奏者的 1.20 米是坐姿手改值
（`sitting` 系数只给 0.92 米初值，她抱着琴、上身略前倾）。

断言：

1. 场景块的层序是"演奏者 / 钢琴 → 合唱团 → 观众"，不是"左 / 中 / 右"；
2. 遮挡只出现"演奏者挡合唱团""琴盖挡合唱团右侧"两条，不出现"中缝"；
3. 俯视图里合唱团在演奏者后方，脚印在 0.4 米的台阶线上；
4. 演奏者坐姿时画面高度明显低于站立高度，场景块写"站立 1.68 米，画面中约 1.2 米"；
5. 提示词里不再出现"the middle band / the gap between / the edge of the stage"；
6. 320 / 360 宽下当前页不溢出，检查器在底部弹层里；
7. 翻页前后选中框与缩放不丢（两页读写同一份 `LayoutScene`）。

投影与求解的单元测试：

- 已知相机 + 已知 3D 框 → 镜头框（golden 数值）；
- 镜头框 + `height` → `z`（往返一致，误差 < 0.5%）；
- 镜头框 + `z` → `height`；
- 站立 1.68 米 + 坐姿系数 → 画面高度 0.92 米（可手改）；
- `yaw=90°` 的脚印取外接矩形后与投影结果一致。

## 11. 风险

1. **用户不知道距离**。默认给一版按身高的推算，并明确标"推算"；用户在俯视图里拖一下就能改准。
2. **站立高度不等于画面高度**。用 `pose` 系数 + 可手改的 `height` 分开处理；
   不要拿站立高度直接投影。
3. **平视假设**。仰拍 / 俯拍会让"镜头视图 = 立面"失效；本设计明确不支持，
   需要时再上 pitch + 第三视图。
4. **联动歧义**。`lock` 只允许一个真源；同一帧里两个视图都改时，以最后一次提交为准，
   并立即重投影另一个视图。
5. **MOSS 只吃轴对齐框**。`yaw` 只能进俯视图与场景块，导出必须取外接矩形并如实记账。
6. **斜面表达不了**。琴盖、屏幕、翻开的书仍是 `tilt` 提示；不要用"盒子旋转"假装解决。
7. **俯视图的比例尺**。自动适配会让物体移动时网格跳动；打开时定一次视野，
   之后用缩放按钮，不要每帧重算。

## 12. 已定与开放问题

**已定（2026-11-11）**

- 人物站立身高**每份布局手填**，不读角色卡；默认 1.68 米，换一份布局要重填。
- 镜头默认水平视场 **50°**，界面上叫「35mm 广角档」。这是产品档位名，
  不按 36mm 画幅做精确换算（真要精确，35mm 对应约 54°）。
- 俯视摆位与镜头视图**翻页切换**，不并排。

**仍然开放**

1. 俯视图的视野：固定 10 米 × 10 米，还是按最远物体自动扩？建议打开时按内容定一次。
2. 台阶 / 台口是场景级的一条基准线，还是每个框自己的 `base`？建议两者都要：
   场景一条默认地面线，框可以覆盖。
3. `yaw` 的 0 度约定：面向相机，还是面向 +Z？建议面向相机（用户直觉）。
4. 相机要不要显示视锥？建议显示，帮助判断"这个物体在不在画面里"。
5. 旧布局的 `surface` 是否彻底废弃？建议先保留为墙面提示，地面关系交给 `base`。
