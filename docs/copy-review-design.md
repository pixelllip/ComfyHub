# AI 文案审校：**独立的简单软件**（设计 v2，2026-09-27 用户拍板）

> ## 先说结论（这一版和 v1 完全不同）
>
> **v1（已废弃）**：把"规则类文案"做成主程序里的**覆盖层**（`copy_overrides` 表 + 七条端点 +
> 运行时注入到系统提示词 / 工具描述 / run-kit / Run 快照）。**已经全部撤掉**：
> Rust 侧那 2209 行与 15 个文件的改动丢弃，Dart 侧那一层用 `aae813e` revert。
>
> **v2（当前）**：文案审校做成**一个独立的简单软件**，**不并入主程序**。
> 范围按用户拍板**只做 B**：
>
> | | 可改？ | 真源 |
> | --- | --- | --- |
> | **skill 正文**（`skill.<name>.body`） | ✅ **可改**（它本来就是磁盘上的文件） | `<storage>\ai\skills\<name>\SKILL.md`、`skills\builtin\<name>\SKILL.md` |
> | **界面注解**（`ui.*`） | ✅ **可改**（直接改主 App 的 Dart 源码文本，改完重新构建 App） | `lib/**` 里那些字面量 |
> | **系统提示词**（`prompt.s<N>` / `prompt.nsfw`） | ⛔ **只读**（可看、可标"我读过"） | `server-rs/src/ai/nsfw_prompt.rs` |
> | **工具描述**（`tool.<name>.description`） | ⛔ **只读** | `server-rs/src/tools/desktop_tools.rs` / `tools.rs` |
>
> **为什么不做覆盖层**（用户的原话是"不合并进我们的主程序"，这里记下我同意它的技术理由）：
> 覆盖层会把"系统提示词 / 工具描述"从**编译期常量**变成**运行时数据** ——
> 好处是能改能审，代价是"这一轮到底用了哪版规则"多一层间接，而**误改的代价**
> （删掉一条纪律 → 模型行为变差，且没人会立刻发现）远大于收益。
> 只读 + 人工校验能拿到"文案没错、我看过了"的九成价值，且**主程序一个字节都不动**。

## 1. 这个软件要解决的问题

| 现状 | 后果 |
| --- | --- |
| 规则类文案散在四处（Rust 常量 / skill 磁盘文件 / Dart 字面量），**没有一份清单** | "某条文案写错了"只能靠撞上（历史上的例子：工具描述写着"提交时也会跑一次审核"，而代码当时根本没跑） |
| 没有"我读过并确认"这个**事实** | 每次改动之后，没人知道哪些话已经被复核过、哪些是新的 |
| 批量改文案只能靠手改 + 全局搜索替换 | 漏改、误改、改完不留痕 |

**它不负责**：改系统提示词（只读）、让模型自己改文案、把文案存进主库。

## 2. 形态

**一个独立的小软件，跑在同一台机器上，不依赖主程序运行**（主程序没起也能用）。

三种候选形态（**待用户挑**，见 §6 问题 1）：

| 形态 | 怎么用 | 代价 |
| --- | --- | --- |
| **(a) CLI 脚本 + 本地 HTML 报告**（推荐） | `pwsh -File scripts\copy-review.ps1 <动作>`；`report` 动作生成一份可在浏览器里看的清单 | 最省事、随仓库走、可进版本库；缺点是"看"这一步要开浏览器 |
| **(b) 单文件本地网页（HTML + JS，无后端）** | 双击打开，清单/校验/diff/批量都在浏览器里；改文件时导出一份 JSON，再让脚本应用 | 交互最舒服；但"写文件"必须借一个脚本，等于两件东西 |
| **(c) 独立的小 Flutter 桌面程序**（单独目录） | 一个真 GUI | 最重（新建一个 Flutter 工程 + 构建链），与"简单"矛盾 |

**共同的内核**（三种形态都复用，所以先做它不会白做）：
`list / show / verify / unverify / set / batch / apply / export / import / report / open / check`。
（`apply` = 浏览器"导出改动"那份 JSON 的**唯一**落盘入口，默认 dry-run，`-Apply` 才写；
`open` 生成自包含 HTML，`check` 只提示不改。2026-09-27 补：`apply` 在 ValidateSet/switch 里漏过，
HTML 与 `open` 的提示却一直在教人敲它 —— 已接上并加自测。）

## 3. 清单从哪来（**不维护第二份真源**）

每条文案一条记录：`{key, scope, title, text, source(file:line), editable, sha256, verifiedAt, note}`。

| scope | 怎么取 | 备注 |
| --- | --- | --- |
| `skill` | 扫两个投放口（`<storage>\ai\skills`、`skills\builtin`），读 `SKILL.md` 正文；frontmatter 单独解析（`name`/`description` 也进清单） | 正文与 frontmatter **分开**两条，改正文不影响 frontmatter（AGENTS §10 的纪律） |
| `ui` | 由**一份显式清单** `scripts\copy-review-ui.json`（key → 文件 + 匹配锚点）指路，文本从**源码里现读** | 清单只记"去哪找"，不记文本 —— 文本永远从源码读，才不会分叉 |
| `prompt` | 解析 `nsfw_prompt.rs`：按 `§N` 切段 + `NSFW_RAW` 那一段 | **只读** |
| `tool` | 解析 `desktop_tools.rs` / `tools.rs` 的 `description` 字面量 | **只读** |

> ⚠ 解析"哪一段是哪一段"必须**有唯一判据**（`§N` 段头 / 具名常量 / 显式清单），
> **不许**用"中文段落切分"这种会随改动漂移的猜法。解析不出来就**如实列不出来**
> （并在报告里说"这些没解析到"），绝不猜一个 key 出来。

## 4. 状态与写回

**状态文件**：`.run\copy-review\state.json`（工具自己的，**不进主库、不进同步**）。
每条记 `{key, sha256, verifiedAt, note}`。

- **`verifiedAt` 绑内容**：`sha256` 与当前文本不等 → 该条的"已校验"自动失效（**默认回到待校验**）。
  这就是"我看过的那一版"与"现在生效的那一版"能对上的唯一办法。
- **写回**（只对 `editable` 的两类）：
  1. 先写 `<file>.copyreview-bak`（同名只留最近一次）；
  2. 再写新内容；
  3. 逐条独立 —— 一条失败不连坐，报告里列清楚。
- **batch**：`find/replace` 或正则；**永远先出 diff**（`--dry-run` 是默认值，要真写必须显式 `--apply`）；
  应用前把命中的每一处都列出来（文件 + 行号 + 前后文），一处也不许"顺手多改"。
- **skill 写回后**：用主程序**现有**的校验（`GET /api/ai/skills` 的 `validationError`，或离线解析
  frontmatter）确认它仍能被加载 —— 主程序不在线时如实说"没做这一步校验"，不假装通过。

## 5. 机器校验（只对 editable 的条目）

| 检查 | 为什么 |
| --- | --- |
| frontmatter 完整性（`name` / `description` 有、YAML 块标量能读） | 主程序靠它注册 skill；坏了的表现是"这个 skill 压根不出现" |
| 占位符不被改坏（`ui.*` 里若有 `{}` 之类） | 改坏会漏出原始标记 |
| 长度预算（skill 正文有上限） | 主程序对正文长度有约束 |
| 只读条目的**一致性提示**：文案里点名的工具必须真在 `IMPLEMENTED` 里 | 这是历史教训（描述说"会跑审核"而代码没跑）；**只提示，不改** |
