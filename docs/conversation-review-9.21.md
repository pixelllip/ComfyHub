# 2026-09-21 与 AI 的对话记录：调研结论与优化清单

> 用户建议 ⑤（2026-09-22）："调研我昨天和 ai 的对话记录，分析还有哪些值得优化的。"
>
> 调研范围：本机数据库 `comfy_hub` 里 **2026-09-21 的 5 场对话**（外加 09-19/09-20 的对照），
> 共 45 条消息、36 次 Run、91 次工具调用。每一条结论下面都写了**证据出处**（会话 id + 序号）。
>
> 结论按"用户能感知的痛"排序，不按代码模块排。

## 0. 一句话结论

**昨天最大的痛点不是"AI 不够聪明"，而是三件事挡住了它：**

1. **工具预算太小**（8 轮 / 16 次），一场"读工作流 → 查节点 → 改参数 → 提交"的活干到一半就被掐断 ——
   用户被迫连发 3 次"继续"；
2. **上游网关不稳定**（21 条 Run 里 13 条失败，其中 11 条是 `PROVIDER_UNREACHABLE`，
   8 条明确是 `SSLHandshakeException`），失败时那条回复是**空的**，用户什么都看不到；
3. **界面格式工作流（rgthree 那套前端节点）转 API 图**这条路反复失败，
   AI 只能反复让用户"去 ComfyUI 导出一份 API 格式"，最后用户自己说了句
   **"你自己搓一个工作流"**（会话 `c8bd4203` seq15）。

## 1. 工具预算在真实使用里就是不够（**已在 09-22 修掉**）

**证据**（原话都来自库里）：

| 会话 | 现场 |
| --- | --- |
| `35157d38` seq3 | "（已达到本次回复的工具轮数上限 8，这次要调用的工具没有执行；再发一条消息它就能接着做。）" |
| `b5233fb4` seq8 | 同一句（那次的活是"读出工作流结构 + 对照本机文件逐个校准"） |
| `90861227` seq4 / seq12 | 同一句（那次要"从文件本身把调好的参数抠出来"，因为 ComfyUI 查询额度也用尽了） |

对照实测：**当天真实 Run 的调用次数中位数 6、最大 18** —— 上限 16 是**擦着用**的，
而"轮数"上限 8 直接决定了 AI 能走几步。两个数字都是按"单次闲聊"设的，
但用户实际在用它做"多步工程"。

**已处理（提交 `7a9b59f`）**：默认值 8 轮 / 16 次 → **16 轮 / 48 次**；
用户回答提问后**重置**额度（用户建议 ③ 的原话）；失败的调用不计数；
绝对天花板 200 次兜底。

## 2. 🔴 上游连接失败是最大的一条：11/13 次失败都是它

**证据**：

```
select error_code, left(error_message,90), count(*) from ai_runs where created_at >= '2026-09-21' group by ...
PROVIDER_UNREACHABLE  上游请求失败：SSLHandshakeException   9
PROVIDER_UNREACHABLE  上游请求失败：IOException             2
RATE_LIMIT            被限流（HTTP 429）                    1
ABORTED               用户已停止 / 请求被中断                5
```

现场形态（会话 `35157d38`、`90861227` 里连续出现）：

- 用户发一条消息 → **AI 一个字都没回**（`ai_messages.text` 长度为 0）→ Run `failed`；
- 用户再发"继续" → 又是一条空回复 → 再"继续"……**四连空**（`35157d38` seq2/5 与
  `90861227` seq8/10 都是这样）。

**为什么值得查**：这不是"网络偶尔抖一下"，而是**同一个错误信息重复出现**，
且 `SSLHandshakeException` 指向的是**证书链 / 代理**问题（本机 `~/.gradle/gradle.properties`
里配了 `127.0.0.1:7890` 代理，说明这台机器是走代理出网的）。

**建议（按性价比排序）**：

1. **错误信息必须带根因**：现在只写 `SSLHandshakeException`，连 `PKIX path building failed`
   或"代理证书不在信任库"这种关键一句都丢了 —— 用户看到等于没看到。
   改法：`AiErrorCode.PROVIDER_UNREACHABLE` 的 message 里带上 `cause` 链（前 200 字符）。
2. **失败的那一轮自动重试一次（只在"一个字都没说出去"时）**：现在
   `runRoundWithFallback` 只对 `CONFIG_ERROR / PROTOCOL_ERROR` 重试，网络抖一下不重试。
   判据可以严格：`text.isEmpty() && step == 0` 才重试一次，指数退避 1s/3s。
   *（这条与"绝不重放已说出去的话"不冲突 —— 那个纪律的前提是有内容。）*
3. **界面把"空回复 + PROVIDER_UNREACHABLE"画成一条可重试的错误卡**，而不是一个空气泡。

## 3. 🟡 界面格式工作流 → API 图：反复失败，最后是用户自己认输

**证据链**（会话 `90861227` / `c8bd4203` / `b5233fb4`）：

- `90861227` seq4：`krea2SFWNSFWUncensoredImageTo_v10` **runnable=false**，
  转换时摘掉 20 个纯前端节点（`Label` / `Fast Groups Bypasser` / `Bookmark` 全是 rgthree），
  摘完留下 6 处缺口；`13.input_image` 空着（**参考图根本没接进 Resize**）。
- 同一个会话 seq6：AI 从文件里抠出参数、自己搭了最小图生图提交，"跑了 40 秒却没有产物文件"。
- `c8bd4203` seq4/6：MiaoMiao Harem 连续两次在 **节点 84 `VAEDecode → SaveImage`**
  的输出校验阶段失败（用户回："我在 comfy 里可以直接跑，是不是你的问题？"，
  AI 承认"更像是我的提交链路问题"）。
- `b5233fb4` seq6：那份 rgthree 工作流的 LoRA 走 `Power Lora Loader`，
  后端拿不到具体文件名 → 无法覆盖参数。
- 最终 `c8bd4203` seq15 用户："**你自己搓一个工作流**" —— AI 自建精简图，一次成功（mediaId 193）。

**结论**：**"自建最小骨干"这条路已经证明比"转换界面格式"更可靠**，
但它现在是"用户被逼出来的手段"，而不是**默认策略**。

**建议**：

1. **改默认**：`comfy_load_workflow` 转换后 `runnable=false` 且缺口 ≥ N 处时，
   **主动提出"我按你这份图的骨干自建一份最小图"**这个选项（现在只是报 `unsupportedNodes`
   让用户去导 API 格式）。昨天那次自建一次就成功，值得从"兜底"提到"首选之一"。
2. **`Power Lora Loader` 这类"参数藏在 JSON 里"的节点**：它的 LoRA 列表是
   `widgets_values` 里的嵌套结构，值得单独解一层（rgthree 在真实用户的工作流里出现频率很高）。
3. 节点 `84` 那种"**在 ComfyUI 界面里能跑、我们提交就挂**"的形态，值得留一份最小的复现用例
   （现在的 e2e 里没有这种"输出键结构错"的场景）。

## 4. 🟡 两条 `running` 的 Run 一直挂在库里

**证据**：`ai_runs` 里有 2 条 `status='running'`，都属于 `90861227`（09-21 23:0x），
而它们的 `updated_at` 之后再没有变化 —— 也就是**后端重启时没有被清掉**。

`Application.kt:302` 确实有 `AiRunRepo.failStaleRunning()`，但它跑在**模块装配**里；
如果那一次启动时 `Migrate.run()` 或装配提前抛错，这行就永远不会执行
（`Application.kt:71` 那处是 `runCatching`，失败只打日志）。

**建议**：把 `failStaleRunning()` 挪到**数据库就绪之后、装配之前**（和 `Migrate.run()` 同一个
`runCatching` 块里），并给它一条用例/启动自检 —— 界面上"永远转圈"是最伤信任的形态。

## 5. 🟢 值得表扬/保留的（别在重构里丢了）

- **"不编"的纪律真的守住了**：`b5233fb4` seq6 里 AI 明确写"这三条是旁证，不是证明"、
  "我没读到结尾，所以有没有 `text_encoders.*`，我现在不知道，不编"。
  这正是系统提示里那条纪律想要的效果，改提示词时别把它稀释掉。
- **`comfy_prune_workflow` 的分析结论真的准**：seq6 里"checkpoint 是裸 DiT、
  必须外挂 CLIP/VAE"的结论与后来实测的日志、safetensors 头部完全一致。
- **产物入 P 链路是通的**：自建工作流那次一次就 `mediaId: 193`，画廊里能看到。
