# 3D 布局：可行性评估与设计草案

> **状态：已搁置（2026-11-03 用户拍板："3D 路线就先弃用"）。**
> 现在的方向是「在 AI 工作台里把提示词与可编辑的 2D 布局同轮交付」，
> 见 [`layout-workspace-design.md`](layout-workspace-design.md)。
> 本文保留作为技术评估：结论（3D 是作者侧模型、出口仍是 2D bbox + 散文）、
> 选型事实（flutter_scene 0.24.3 / Flutter GPU）与分期估算都仍然成立，
> 哪天要做时从这里接着走；**不要再把它当成待实施的计划**。
>
> 2D 版的现状见 [`layout-translator.md`](layout-translator.md) 与
> `lib/models/layout_spec.dart` / `lib/pages/layout_canvas_page.dart`。

## 0. 结论

**方向成立，可行，而且比"把 2D 画布做得更好用"更接近真问题。** 但要先把三件事说清楚：

1. **3D 是作者侧的模型，不是新的出口。** 下游仍然只吃两样东西：MOSS 布局 JSON 的
   2D bbox，和一段散文。3D 的价值在于**由几何自动推出这两样**（投影、遮挡、表面归属、
   景深顺序），而不是"让画面看起来像 3D"。如果 3D 场景不能投影回 2D 坐标，精度就丢在
   出口上，等于白做。
2. **它替掉的是枚举，不是画布。** 现在 `surface`（左墙/右墙/正墙/地面/桌面）和
   `camera`（俯视/平视/仰视）都是"2D 表达不了 3D"的补丁（`layout_spec.dart` 第 11~48 行
   的注释自己写了原因）。3D 里这两件事是**算出来的**，不用用户选。
3. **它不解决模型的服从度，也不解决轮廓。** `layout-translator.md` 里"深度图试过、删了"
   那节已经证明：体块没有真实轮廓。3D 体块能给出位置、比例、遮挡关系，给不出人是不是圆的。
   "精确"只能承诺到**规格**这一层，承诺不到出图。

给 flutter_scene 的结论：**0.24.3 可用**（Flutter 3.47+，Windows / Android 都在支持列表里），
内置几何（`CuboidGeometry` / `PlaneGeometry` / `CapsuleGeometry` / 线段）意味着**不需要素材管线**
就能先做体块布局；拾取、轨道相机、`ui.Image` 抓帧都是现成的。代价是它 **pre-1.0**
（minor 版本带 breaking change）、**Flutter GPU 默认关闭**（要按平台显式打开，Windows 发布
构建还需要 3.47.1+ 的 `DartProject` 设置），以及 **`flutter test` 里没有 GPU**。

## 1. 为什么 2D 不够（用现有实现当证据）

- **同一段关系，2D 只能靠"猜"**：床在右墙前、镜在左墙，用户在屏幕上画的是两个互相
  垂直的矩形，画完必须再手动选 `surface`，否则散文只能说"画面左侧"。用户原话已经
  写在 `layout-translator.md`："我要的不是这种平面场景，比如镜面在一堵墙上，而床和窗户
  在紧挨着的另一堵墙。"
- **相机是形容词**：`LayoutCamera` 只有三档，俯视/平视/仰视说不清"机位 1.6 米、下俯 3°、
  50° 竖直视角"。而透视、地平线、画面里能看见多少桌面，全由这三个数决定。
- **改比例要重画**：2D 框是画面归一化坐标，换 3:4 → 16:9 等于所有框重摆。3D 里换的只是
  裁切框，场景不动 —— 这是"同一场景多机位/多画幅"的前提。
- **遮挡是手填的**：`inFront` 关系要用户指认。3D 里谁在前是几何事实。
- **镜像要手填，而且常常填错**：`mirror` 关系现在靠人选目标框。3D 里给一面镜子，
  反射框可以直接算出来（见 §3.5），连"镜中看不看得见"都能判定。

## 2. 3D 能多给出什么（只列"能进 JSON / 散文"的）

| 能力 | 怎么来的 | 进哪条出口 |
| --- | --- | --- |
| 精确 bbox | 世界坐标 → 视图/投影矩阵 → 裁剪 → 0~1000 | MOSS JSON（形状不变） |
| 表面归属 | 物体锚点落在哪个面（地面 / 左墙 / 正墙 / 桌面） | 散文 + `surface` 字段（兼容） |
| 前后景与遮挡 | 低分辨率 z-buffer 或投影重叠 + 深度 | 散文（"挡住床的左下角约两成"）、`inFront` 自动 |
| 朝向 | `rotY` 与相机的关系 | 散文（正面 / 侧身 / 背对） |
| 尺度一致 | 米制尺寸（人 1.7m、床 2m） | 散文（"床长约两米，占画面宽度四成"） |
| 机位与地平线 | 相机高度 / 俯仰 / FOV / aspect | 散文开头（现有模板只有"平视视角"四个字） |
| 镜像框 | 镜面反射矩阵 | 散文 + 一个可选的镜像 bbox |
| 一场景多画幅 | 同相机换 aspect / FOV | 保存多份"镜头"，不用重摆 |

**给不出的**：物体轮廓、材质、光照风格、"模型一定照做"。这三条要么来自素材，要么来自
生成结果（`layout-translator.md` §深度图），3D 体块都替代不了。

## 3. 技术选型：flutter_scene 0.24.3

### 3.1 事实（2026-11-02 查 pub.dev）

- `flutter_scene 0.24.3`，**pre-1.0**：minor 版本可能带 breaking change。
- 要求 **Flutter 3.47+**；本机是 3.47.9 ✓。
- 渲染走 **Flutter GPU**，**默认关闭**，要按平台打开：
  - 开发：`flutter run --enable-flutter-gpu`；
  - Windows 发布：`windows/runner/main.cpp` 里 `project.set_enable_flutter_gpu(true);`
    （需要 3.47.1+，本机满足；发布构建会把命令行开关编译掉，所以必须写进 runner）；
  - Android：`AndroidManifest.xml` 的 `<application>` 里加
    `<meta-data android:name="io.flutter.embedding.android.EnableFlutterGPU" android:value="true" />`。
- 平台：Windows / Android 都标 🟢；Windows / Linux **发布**要 3.47.1+。
- 内置几何：`CuboidGeometry`、`PlaneGeometry`、`CapsuleGeometry`、`CylinderGeometry`、
  `LineSegmentsGeometry` 等 → **体块与线框不需要 GLB、不需要 `flutter_scene:init` 素材管线**。
- 能力：`SceneView` + `PerspectiveCamera`、轨道/飞行相机控制器、**raycast 拾取**、
  `ui.Image` 同步抓帧、把 Flutter widget 贴到 3D 面、glTF 导入。

### 3.2 为什么仍然要留一个"软件渲染"兜底

三条硬约束，不是洁癖：

1. **`flutter test` 里没有 GPU**。布局的回归（投影、bbox、遮挡、迁移）必须能在 CI / 本机
   `flutter test` 里跑，不能靠截图肉眼比。所以**几何、投影、拾取判定、输出**必须是纯 Dart；
   渲染器只负责画。
2. **低端 Android 不一定有可用的 Impeller/Flutter GPU**。3D 页打不开时，至少要让用户还能
   用体块线框把布局摆完（软件投影 + `CustomPainter` 画线框/深度排序填充），而不是整页报错。
3. **pre-1.0 的依赖要可拔**。渲染器藏在接口后面，升级/回退只动一个文件；这也符合仓库对
   `video_player_win`、`webview_all` 的做法（钉版本 + 不顺手升级）。

所以架构是：**纯 Dart 场景内核 + 两个渲染器**（flutter_scene 优先、CustomPainter 兜底），
不是"页面里直接堆 SceneView"。

### 3.3 模块落点（建议）

```
lib/models/layout_scene.dart        // Scene3D / SceneObject / SceneCamera / Room（纯 Dart，无 GPU）
lib/core/layout_projection.dart     // 视图/投影矩阵、近平面裁剪、bbox、0~1000 映射
lib/core/layout_visibility.dart     // 低分辨率 z-buffer：可见比例、可见 bbox、遮挡者
lib/widgets/layout_scene_view.dart  // 渲染器接口 + flutter_scene 实现
lib/widgets/layout_scene_painter.dart // 兜底渲染器（同一个接口）
lib/pages/layout_3d_page.dart       // 编辑器（三视图、面板、手势）
```

`lib/models/layout_spec.dart` 只加一个可空的 `scene` 字段与 v2 序列化；**翻译函数
（`translate()` / warnings）继续是纯函数**，这是"模板兜底 + 手机端也能用"的前提。

## 4. 数据模型 v2（草案）

```jsonc
{
  "v": 2,
  "width": 1024, "height": 1365,          // 输出像素；宽高比 = 相机 aspect
  "brief": "雾夜废墟……",
  "camera": { "x": 0.0, "y": 1.6, "z": 3.2, "yaw": 0, "pitch": -3, "fov": 50 },
  "room":   { "w": 4.0, "d": 4.0, "h": 2.7, "walls": ["back", "left"] },
  "objects": [
    { "id": "r1", "label": "镜子", "caption": "圆形铜框镜", "kind": "object",
      "shape": "plane", "size": [0.6, 0.9, 0.03],
      "pos": [-1.97, 1.5, 0.4], "rotY": 90, "anchor": "left" }
  ],
  "overlays": [                            // 屏幕空间层：文字 / 留白（仍然是 0~1000）
    { "id": "r9", "kind": "text", "rect": [80, 820, 840, 90], "text": "废墟之下" }
  ]
}
```

约定：

- **单位：米**；**右手系、+Y 向上**；`yaw = 0` 朝 `-Z`（相机在房间正面，看向后墙）。
  `pos` 是**底面中心**（落地物体好摆），`anchor` 决定它贴哪个面。
- **相机 = 位置 + yaw/pitch + 竖直 FOV**；`aspect` 从 `width/height` 来。不存 look-at
  目标（可由前四项推出），避免两份真源。
- **`overlays` 是刻意的 2D 层**：文字框和留白是"画面上的东西"，不是房间里的东西。
  强行做成 3D 平面只会让"文字大小随透视变化"变成新问题。
- **`regions` 不存**：它是 `objects ∪ overlays` 的投影结果。v1 的 `regions` 仍然能读，
  读出后**每个框当一张朝向相机的 billboard**（深度固定 4m），投影回去与原来的
  0~1000 矩形逐像素一致 —— 老布局打开不变形，再逐个"抬"进 3D。
- 关系字段保留：`same` 仍然手填（两格漫画里的同一个人），`mirror` 在有镜面物体时
  **自动推导**，`inFront` 由遮挡计算**覆盖**（用户手填的值只作为"期望"提示，冲突时警告）。

## 5. 投影与可见性

1. `view = Rᵀ · T(-eye)`，`proj = perspective(fovY, aspect, near=0.05, far=100)`；
   NDC → 屏幕：`x = (ndc.x·0.5+0.5)·W`，`y = (0.5−ndc.y·0.5)·H`（Flutter 的 y 向下）。
2. **近平面裁剪**：相机空间 `z ≤ -near` 的顶点要裁（Sutherland–Hodgman），否则相机后面
   的盒子会投出"镜像"的大矩形 —— 这是 3D 投影最经典的假阳性。
3. **bbox**：盒子的 8 个角投影后取并集（凸包的投影 = 投影的凸包，角点足够）。
   再裁到画幅内，映射到 0~1000；部分出画要按"被裁掉多少"写提示。
4. **可见性**：在 480×640 左右的低分辨率上做一次软件 z-buffer，逐物体统计可见像素 →
   （a）可见 bbox，（b）遮挡比例，（c）谁挡了谁。纯 Dart、确定性、可单测；
   完全不可见的物体**不写进 MOSS JSON**（否则等于让模型画一个看不见的东西），
   只在散文里说"被…完全挡住"并给警告。
5. 性能：几十个盒子、一次重算 < 2ms（体块光栅化只有面片，不做纹理）。

## 6. 交互

3D 自由拖动是最容易被低估的成本。建议**三视图 + 数值**，而不是只给一个透视视口：

- **透视视口**：轨道相机；点选（raycast）；拖动选中的物体（沿它所在的面，射线-平面求交）；
  贴面吸附；选中框用线段几何画。
- **平面图（俯视）**：精确摆 X/Z 与转向；家具/人/墙的关系在这里最清楚。
- **立面图（前视）**：精确摆高度、挂墙、判断遮挡；这就是"两面墙"场景的主编辑面。
- **相机面板**：机位高度、俯仰、水平角、FOV、画幅比例（1:1 / 3:4 / 4:3 / 16:9…）；
  视口里画一个**画幅框**（画幅外的部分压暗），换比例时场景不动、只动框。
- **数值字段**：位置 / 尺寸 / 旋转都能直接输入 —— 拖拽给感觉，数值给精确。
- **手机**：单指轨道、双指缩放/平移、点选；平面图/立面图本身就是 2D 画布，天然适配。
  3D 只做"看 + 粗调"，精细调整引导到数值与正交视图。

## 7. 出口 v5

**散文（模板，纯函数）**新增，按这个顺序：

1. 画幅比例 + **机位**（高度 / 俯仰 / FOV）+ **地平线位置**（由 pitch 与画幅算）；
2. 房间（几面墙、墙角在画面哪里 —— 由墙线投影算，不再让用户描述）；
3. 物体按**深度从近到远**逐段：投影方位 + 表面 + 朝向 + 尺度 + 遮挡 + 点名否定；
4. 镜面单独一段：镜中是谁、在画面哪、与本人是否同一侧翻转。

**MOSS JSON**：形状一个字节都不改。`bbox` 用**完整投影框**（不是可见框），
被裁出画幅的夹回边界并给警告。

**校验器**（`layout_translate.rs`）多一条 3D 才有的确定性检查：**深度词一致性** ——
正文里"前景/中景/背景"的说法必须与算出来的深度排序不矛盾。方位/覆盖/关系三条沿用。

`TRANSLATOR_VERSION` 从 `layout-translator/4` bump 到 `/5`（入参形状变了）。

## 9. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| Flutter GPU 默认关闭 | SceneView 全黑，日志无错 | dev 脚本加 `--enable-flutter-gpu`；发布写进 `main.cpp` / manifest；启动时探测，不可用就退兜底渲染器 |
| pre-1.0 breaking | 升级后编译不过 / 渲染变样 | **钉死 `0.24.3`**（不带 `^`），与 `webview_all` 同一纪律；渲染器在接口后面 |
| `flutter test` 无 GPU | 页面用例跑不了 | 几何/投影/输出全纯 Dart；渲染器只做冒烟（真机手测） |
| 3D 拖动难用 | 用户摆不准，回到 2D | 平面图/立面图 + 数值 + 吸附；3D 视口只做粗调 |
| 视野外/相机后 | bbox 爆炸成整屏 | 近平面裁剪 + 出画/背后判定 + 警告，不写进 JSON |
| 包体变大 | 发布包从 ~14MB 涨 | 实测；只引核心包，不引物理/音频/编辑器 |
| 过度承诺 | "3D 了所以构图一定准" | A/B 验收（§10）；出口仍是 bbox + 文字，模型服从度是另一回事 |
| 范围蔓延 | 要素材库、要真实渲染 | 非目标写死（§11）；GLB 人形/家具放 P6 之后 |

## 10. 验收

1. **几何单测**：已知相机 + 盒子 → bbox 与手算值差 ≤ 1px；相机后的盒子被裁掉；
   跨画幅的盒子按预期夹边；换 aspect 时同一物体的投影比例符合透视。
2. **迁移**：v1 布局 → billboard → 投影回去，0~1000 坐标与原来完全一致；
   保存成 v2 再打开，场景逐字段相等。
3. **输出**：同一场景，MOSS JSON 与手算 pixel bbox 一致；完全遮挡的物体不在 items 里；
   散文里"前景/背景"与深度排序一致。
4. **平台**：`flutter analyze` 0 issue；`flutter test` 全绿；Windows debug 与 **release**
   都能出画面（release 才能证明 `set_enable_flutter_gpu` 生效）；Android debug 真机出画面。
5. **A/B（决定"更精确"是否成立）**：三个场景（墙角双墙 / 镜面 / 前景遮挡），同一工作流、
   同一 seed，2D 规格 vs 3D 投影规格各跑一轮，人工判"表面关系、前后景、机位"三类错误数。
   3D 不占优就说明收益只在作者体验，不在出图 —— 也要如实写进结论。

## 11. 非目标

- 不做照片级渲染 / 材质 / 灯光编辑（用 flutter_scene 的默认 studio 环境就够）；
- 不做深度图导出（已证伪，见 `layout-translator.md`）；
- 不做物理、动画、骨骼（人形先用胶囊/体块）；
- 不做"3D 场景直接生成"（出口仍然只有散文 + MOSS JSON）；
- 不在这一版做素材库与 GLB 导入。

   而不是直接删掉 2D 页。
2. **手机端范围**：建议桌面全功能；手机=看 + 平面图摆位 + 文字层，3D 视口只读。
