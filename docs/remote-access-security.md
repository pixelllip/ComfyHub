# 公网远程控制（电脑与手机异地）：可行性、路径与安全底线（2026-09-22）

> 缘起：`docs/bug and suggestion/bug-and-suggestion-9.22.md` 的建议 ⑥ ——
> 用户问："**有可能在完成配对之后，使用公网远程控制电脑（电脑和手机在异地）吗？安全性如何保证？**"
>
> 这份文档回答两件事：**能不能**（能，且不需要为用户新写一套远程协议）、
> 以及**凭什么敢**（每条都在代码里指得出出处，每条安全主张都说了它的失效条件）。
>
> 前置设计（**必须先做**）：[`inbound-auth-design.md`](inbound-auth-design.md)（配对令牌闸门 P0/P1/P2）。
> 现状与排期：[`android-client-plan.md`](android-client-plan.md) §4。

---

## 1. 结论先行

| 问题 | 答案 |
| --- | --- |
| 技术上可能吗 | **可能**，而且不用改架构：后端本来就是一个 HTTP 服务（`Config.kt` 的监听地址 + 媒体路由 + SSE 事件流），把"能连到它"这件事解决掉就是全部 |
| 今天能直接用吗 | **不能**。今天开远程（`COMFYHUB_ALLOW_REMOTE=1` → `0.0.0.0`）**一个 token 都没有**，`Application.kt` 只打一句 warn 不拦请求 —— 也就是"裸奔"。**先把 `inbound-auth-design.md` 的 P0 做完**，再谈公网 |
| 推荐哪条路 | **虚拟组网（Tailscale / ZeroTier / WireGuard）优先**；要"不装客户端、手机浏览器直接开"就用 **Cloudflare Tunnel + Access**；**最后**才是端口映射 + 反代 + 令牌 |
| 安全性靠什么 | 四层叠加，**缺一层都不算够**：① 网络层"外网根本扫不到这个端口"；② 传输层 TLS（否则令牌在公网上明文飞）；③ 应用层配对令牌（`X-ComfyHub-Token`，常数时间比较 + 失败限速）；④ **能力层不因"来自手机"而放宽**（审批档、工具白名单、写目录一律照旧） |
| 最大的误解 | "配对过了 = 安全了"。**配对只解决"你是谁"，不解决"这条链路会不会被人截、这台机器会不会被人打"** —— 令牌在明文 HTTP 上是可被中间人拿走的，而拿走后他拿到的是**能花你钱、能读你工作流、能驱动你显卡**的能力（见 `inbound-auth-design.md` §2 那张资产表） |
| 明确不做 | 不做"公网直连 + 只靠一个长期令牌"；不做端口映射到裸 HTTP；不做"来自非回环就自动允许工具"（见 §6） |

## 2. 今天的现状（代码事实，不是印象）

| 事实 | 出处 | 影响 |
| --- | --- | --- |
| 默认只绑 `127.0.0.1` | `Config.kt:57` | 默认状态下**公网/局域网都连不上**，这本身就是最强的一层防护 |
| `COMFYHUB_ALLOW_REMOTE=1` → `0.0.0.0` | `Config.kt:55-57` | 一开就听所有网卡 |
| 非回环监听只 warn、不拦 | `Application.kt:305-310`（`if (!ctx.cfg.loopbackOnly) log.warn(...)`） | **裸奔**：谁连上都算数 |
| 全仓没有认证 | `Application.kt:312-392` 装的插件里没有 Authentication；`server/build.gradle.kts` 无 `ktor-server-auth` | 没有任何"你是谁"的概念 |
| CORS 只允许本机来源 | `Application.kt` 的 `install(CORS)` | 挡的是**浏览器跨站**，挡不住 `curl` / 手机 App（非浏览器请求不受 CORS 约束） |
| 后端持有高价值能力 | 见 `inbound-auth-design.md` §2 | Provider Key（能花钱）、文件读写、ComfyUI 提交（烧显卡）、媒体原件（含 NSFW） |
| SSE 不是 `EventSource` | `inbound-auth-design.md` §C3 | 令牌能走 header，但媒体字节（`Image.network` / 视频）**带不上 header** → 必须走"URL 短期签名"（§D5） |

> 一句话：**现在缺的不是"怎么连过去"，是"连过来的是谁"**。所以顺序不能反。

> **2026-11-08 补充**：如果要"手机不装 VPN 客户端也能异地连"，见
> [`cross-network-connection-design.md`](cross-network-connection-design.md) ——
> 自建 WSS 中继，桌面**出站**连接、不暴露入站端口。本文 §3.1 的 Tailscale 仍是
> "零代码、最安全"的那条；两条路不冲突。

## 3. 三条路（按推荐度排序）

### 3.1 虚拟组网：Tailscale / ZeroTier / WireGuard（推荐）

```
手机（装了同一个组网客户端）── 加密隧道 ──▶ 电脑的"组网内网 IP" ──▶ 后端 :8080
公网上的其他人：**不知道也扫不到**这个 IP（它不在公网路由表里）
```

- **连法**：手机与电脑加入同一个虚拟网络，后端**继续绑组网网卡**（或仍听 `127.0.0.1` + 用组网的
  "转发/子网路由"能力），手机访问 `http://<组网IP>:8080`。
- **为什么优先**：端口**对外不存在**（不是"挡住了"，是"扫不到"），这比任何应用层鉴权都硬；
  Tailscale 系的设备身份是**基于密钥的**（每台设备一把，可单独吊销），
  与我们自己的配对令牌形成**两层独立身份**（组网那层 + 令牌那层）。
- **代价与失效条件**：
  - 要在手机上装一个客户端（不是"点开浏览器就能用"）；
  - 依赖第三方协调服务器做握手（自建 Headscale 可以摆脱）；
  - **它只保证"链路与对端身份"，不保证后端安全**：组网内其它设备（同事、家人、被入侵的设备）
    仍然是"非回环"来源 —— 所以**配对令牌该有还得有**（`inbound-auth-design.md` D1 的回环豁免
    是按 **来源 IP 是不是回环** 判的，组网 IP **不是**回环，所以会自动要求令牌。这正是我们想要的）。
- **官方文档**：[Tailscale Funnel](https://tailscale.com/docs/features/tailscale-funnel)（把服务开给公网，
  与本条的"只给组网内"是两个不同的能力，**我们要的是后者**）。

### 3.2 Cloudflare Tunnel + Access（要"手机浏览器直接开"时选这条）

```
手机浏览器 ── https://你的域名 ──▶ Cloudflare（TLS + Access 策略）── 出站长连 ──▶ 后端 :8080
家里路由器：**一个入站端口都不用开**
```

- **连法**：电脑上跑 `cloudflared`（**出站**长连接），Cloudflare 侧配一条 Access 策略
  （只允许你的邮箱/身份，或一个 Service Token），媒体与 SSE 都走 https 域名。
- **为什么好**：① 不用在路由器上开端口（`no inbound firewall rules needed`）；
  ② 自动有**受信任的 TLS 证书** —— 这一条很关键，因为明文的公网 HTTP 上令牌会被中间人拿走；
  ③ Access 是**独立于我们令牌的第二道身份**（我们代码里一行都不用改）；
  ④ 手机端零安装（浏览器即可），配合 P2 的二维码配对最顺。
- **代价与失效条件**：
  - 需要一个**托管在 Cloudflare 的域名**（要花钱买域名，Tunnel/Access 本身有免费额度）；
  - 数据**经过 Cloudflare**（TLS 在 Cloudflare 侧终止，理论上它能看见明文）；
  - `cloudflared` 崩了 = 远程断了（本机不受影响）；
  - 免费版的 Access 策略有次数上限（按人头算），个人用够。
- **官方文档**：[Connect your internal network services](https://developers.cloudflare.com/use-cases/apis/internal-services/)
  （原文摘要：Tunnel 是"outbound-only connections with no inbound firewall rules"，
  Access 负责"Verify identity and enforce per-service policies for every request"，
  Service Tokens 用于"non-interactive credentials for machine-to-machine authentication"）。

### 3.3 端口映射 + 反向代理 + 配对令牌（**最后**才用，且必须 TLS）

- **连法**：路由器把 `443` 映射到本机反代（Caddy / nginx），反代加 TLS 并把 `/` 转给 `:8080`；
  后端要求 `X-ComfyHub-Token`。
- **代价**：这是**真的把服务放到公网**上 —— 会被全世界的扫描器 + 漏洞扫描 + 爆破持续敲门。
  所以它必须同时满足：
  1. **只有 TLS（443）**，不做 80 → 重定向以外的任何明文入口；证书用 Let's Encrypt 自动续；
  2. 后端**只绑 `127.0.0.1`**（由反代转发），**不**绑 `0.0.0.0` —— 否则 8080 也能被直接扫到；
  3. 反代层做**限速与来源限制**（有固定公网 IP 就只放行它；没有就上 fail2ban 一类的封禁）；
  4. 关掉一切不必要的路径与方法（我们只有 GET/POST/DELETE，别的直接 444/403）；
  5. **更新纪律**：这条路把"你有没有及时升级"变成安全前提（公网暴露 = 漏洞的价值变高）。
- **不推荐的变体**：`frp` 之类的内网穿透工具本身没问题，但**必须用它的安全档**
  （frp 官方有一篇专讲"安全地暴露内网服务"的文档，就是 stcp/xtcp 那套 —— 只有**同样知道密钥的
  对端**才能连）。**裸 frp + 一个短 token** 等价于 §3.3 的最差形态。

## 4. 安全靠什么（四层，缺一层都不算够）

| 层 | 作用 | 我们这边谁负责 | 失效条件（说清楚才知道什么时候不管用） |
| --- | --- | --- | --- |
| ① 网络层 | **外网扫不到这个端口** | 组网 / Tunnel（§3.1、§3.2）；或路由器只映射 443 + 后端只绑回环 | 端口映射写错、UPnP 被自动打开、走了 §3.3 的最差形态 |
| ② 传输层 | **令牌与媒体不被中间人截走** | TLS（Tunnel 自带 / 反代证书）；组网自带端到端加密 | 明文 HTTP + 公网 = 令牌等于公开；自签证书会让手机端拒绝或弹警告（别教用户"点继续"） |
| ③ 应用层 | **请求是不是配对过的那台手机** | `inbound-auth-design.md` 的 `X-ComfyHub-Token`（D1 回环豁免 / D4 明文只回可信请求 / D5 媒体短期签名 / D6 SSE 双认 / D7 绑 0.0.0.0 但没启用令牌就拒非回环 / D9 常数时间比较 + 失败限速） | 令牌泄漏且没有 ②（明文链路）、令牌写在 URL 里被日志/历史记录留存（所以媒体走**短期签名**而不是把长期令牌塞进 URL） |
| ④ 能力层 | **不许因为"来自手机"就放宽任何权限** | `ToolPolicy`（写只允许 `<根>\comfyui`，`.git`/`.mysql`/`.run` 永远禁写）、审批闸门 `ToolApprovalGate`、工具 `deny`/`ask` 档 | 有人为了"手机上少点几下"把 `comfy_submit` / `write_file` 改成 allow；或新增一个"远程专用"的放宽分支 |

**最关键的一条是 ④**：前三层防的是"别人进来"，第四层防的是"我们自己把门开得更大"。
手机与电脑异地时，**用户不在电脑前**，所以"要批准的工具"会一直卡在审批超时（默认 5 分钟）
—— 这是**特性不是 bug**：审批必须在手机上弹（P1 之后手机端能看到工具卡），
而不是因为"人不在旁边"就自动放行。

## 5. 配对与令牌：异地场景下的具体要求

沿用 `inbound-auth-design.md` 的 P0/P1/P2，异地场景额外要求：

1. **二维码只用于初次配对**：一次性、有有效期（建议 120 秒），兑换用 `POST`（令牌**不进 URL**），
   兑换请求本身必须走 TLS（否则令牌在第一次就漏了）。
2. **手机侧把令牌存进系统密钥库**（Android Keystore / iOS Keychain），**不落明文文件**；
   桌面侧继续用现有凭据设施（那套**故意不让你读回明文**，见 `inbound-auth-design.md` §C4）。
3. **一机一令牌 + 可单独吊销**：手机上丢了就吊销那一个（设置页里要能看到"哪台设备、最后活跃时间"），
   不是"改一个全局密码"。
4. **媒体走短期签名 URL**（`inbound-auth-design.md` D5）：异地场景下用户会把图片链接转发出去，
   签名过期后链接自动失效 —— 长期令牌则永远有效。
5. **失败限速**（D9）：公网/组网里都会有人敲门，令牌比较要常数时间，失败要按来源限速，
   并且**失败日志里不许回显令牌**（现有出网代码已经有这条纪律：错误里只出现状态码）。
6. **多设备并存**：电脑与手机同时在线时，SSE 是两条独立连接（`RunEventBus` 按 Run 分发）；
   谁的请求归谁答案，不要做成"远程接管"（那会变成两个人抢一个会话）。

## 6. 明确的安全红线（写进代码，不靠自觉）

| 红线 | 为什么 |
| --- | --- |
| **非回环来源也必须有令牌**（回环才豁免） | 组网 IP、Tunnel 来的请求都**不是**回环 —— 这条让 §3.1/§3.2 自动落在保护里 |
| **不许新增"远程专用"的放宽分支** | 一旦有 `if (fromPhone) skipApproval()`，④ 层就没了；能力只认用户设置，不认请求来自哪里 |
| **远程不改变写白名单** | 写仍然只允许 `<根>\comfyui`；`.git` / `.mysql` / `.run` 永远禁写（`ToolPolicyConfig.FORBIDDEN_SEGMENTS`） |
| **长期令牌不进 URL、不进日志** | URL 会被浏览器历史、中间代理、聊天软件留存；日志会被备份与转发 |
| **明文 HTTP 只允许回环** | 绑定 `0.0.0.0` + 没有令牌 → **拒绝非回环请求**（D7），而不是"能连但没保护" |
| **远程开关默认关**，且开启前跑一次自检 | 见 §7 |

## 7. 开启远程前的自检清单（UI 里逐条列出来，`up`/`doctor` 也能打印）

1. 后端**只**通过 §3 的某一条路径可达；`http(s)://<公网IP>:8080` **连不上**（这条最容易被无视）；
2. 链路是 **HTTPS**（或组网自带加密），证书受信任；
3. 配对令牌已生成、已存进手机密钥库、**能单独吊销**；
4. 失败的登录尝试有限速、有日志、日志里没有令牌；
5. 工具权限档**没有被为了远程而放宽**（特别是 `comfy_submit` / `write_file` / `comfy_use_attachment`）；
6. ComfyUI 的 `8188` **没有**暴露到公网（它自己没有任何鉴权）；
7. 电脑不自动睡眠、后端随开机自启（异地时"电脑睡着了"= 掉线，用户会以为是软件坏了）；
8. 远程端**能看到并处理审批卡**（否则工具会在 5 分钟后超时被当作拒绝，用户看到的是"什么都没做"）。

## 9. 落地顺序（建议）

1. **P0 令牌闸门**（`inbound-auth-design.md` §6）—— **没有它，下面一步都别做**；
2. **P1 手机能看图**（媒体短期签名 + SSE header/`?token=` + 手机上能看到审批卡）；
3. **一条远程路径**：先在**组网**里跑通（不需要买域名、不受公网扫描），验证 P0/P1；
4. **P2 二维码配对 + 设备管理页**（一机一令牌、吊销、最后活跃）；
5. 想做"浏览器直接开"时再加 Cloudflare Tunnel + Access，并把 §7 的自检清单做成界面上的检查项。

> 一句话收尾：**远程不难做，难的是"远程之后，链路与身份都还站得住"。**
> 组网或 Tunnel 解决链路，配对令牌解决身份，**审批闸门与写白名单解决"手机丢了怎么办"** ——
> 三样都在，异地控制才是一个可以打开的功能；少一样，它就是一个把整台电脑交出去的后门。
